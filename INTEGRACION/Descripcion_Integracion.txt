MODULO DE INTEGRACION SND - PERSISTENCIA Y REENVIO

Requisitos: Windows, Visual Studio, .NET Framework 4.7.2, SQL Server/LocalDB.
Restaurar los paquetes NuGet antes de compilar.

INSTALACION
1. Ejecutar SQL/Crear_INAIPI_Integracion.sql en la instancia SQL elegida.
   El script crea la base y tabla si no existen. No migra tablas existentes.
2. Ajustar CnIntegracionDb en Web.config a esa instancia.
3. Ajustar CoreBaseUrl al puerto de INAIPI.Core.Services.
4. Recompilar y ejecutar Integracion; abrir /swagger para iniciar la aplicacion.

ENDPOINTS
GET /api/telemetria/ping verifica que Integracion responda, no la disponibilidad de CORE.
POST /api/caja/sincronizar valida y almacena el lote.
HTTP 202 confirma almacenamiento, no persistencia en CORE.
HTTP 400 indica validacion fallida. HTTP 503 indica fallo de almacenamiento.
Usar GUID nuevos para operaciones nuevas. Un GUID existente conserva los datos originales.

PERSISTENCIA
Data/PendientesRepository.cs guarda el lote en una transaccion SQL.
La clave primaria evita filas duplicadas por GUID.
Estados: Pendiente, Sincronizada, Rechazada. EnProceso esta reservado; esta version no lo utiliza.
Intentos cuenta ciclos de envio, no cada intento HTTP.
FechaRegistro se normaliza a UTC; enviar fechas con zona horaria explicita.

PROCESADOR
Global.asax inicia ProcesadorPendientes mediante QueueBackgroundWorkItem.
Selecciona hasta 20 pendientes cuyo ProximoIntentoUtc ya llego o es NULL.
Un bloqueo de sesion SQL evita ciclos concurrentes de este procesador en la misma base.
Solo el procesador realiza los envios; el endpoint no envia directamente.
ResilienciaService realiza hasta cuatro intentos con esperas de 1, 2 y 3 segundos.
Codigo CORE 200: Sincronizada. Codigos >=500, 408 o 429: Pendiente.
Otros codigos: Rechazada; revisar datos y logs antes de reactivar.
Tras fallo temporal se programa ProximoIntentoUtc a 30 segundos.
Tras cada ciclo el procesador espera 30 segundos; el intervalo real incluye el tiempo de los envios.

PRUEBA
1. Dejar SQL e Integracion ejecutandose y detener solamente CORE Services.
2. Enviar desde Swagger un lote con centro/beneficiario validos y GUID nuevos.
3. Verificar registros Pendiente en INAIPI_Integracion.dbo.TransaccionesPendientes.
4. Iniciar CORE sin reenviar el lote.
5. Verificar Sincronizada y FechaSincronizacionUtc, y registros en tblAtenciones.
6. Revisar logs con el GUID. Logs registra diagnostico, no sustituye la tabla.

LIMITACIONES
El procesador vive en ASP.NET: al detener IIS Express o reciclar la aplicacion se interrumpe.
Los registros permanecen en SQL y se retoman cuando la aplicacion vuelve a arrancar.
No garantiza ejecucion si el sitio esta detenido o inactivo; para produccion usar un servicio independiente.
Si SQL tambien esta caido, no puede aceptar nuevas transacciones de forma segura.
CORE debe garantizar idempotencia por TransaccionGuid: si pierde una confirmacion se puede reenviar.
Esta version no compara los datos de GUID repetidos ni recupera registros EnProceso.
No subir credenciales, logs, datos personales ni archivos mdf/ldf a GitHub.
